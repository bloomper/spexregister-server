[[prerequisites]]
== Prerequisites

You need to have the following installed to run Spexregister Server:

* Docker
** Version 29.0.1 is verified to work

You also need the following if you are to do development in Spexregister Server:

* Git
* Java
** Version 25 is required, later versions might work as well
* Gradle
** Version 9.2.1 is verified to work
* An IDE of your choice

[[cloning_the_repository]]
== Cloning the repository

Clone the Git repository:

[source,bash]
----
$ git clone https://github.com/bloomper/spexregister-server
----

Add the following to `/etc/hosts` (or the Windows equivalent):

[source,bash]
----
###################################
#          Spexregister           #
###################################
127.0.0.1 keycloak.fgv.local.nu
127.0.0.1 api.register.fgv.local.nu
127.0.0.1 register.fgv.local.nu
127.0.0.1 mail.fgv.local.nu
----

[[run]]
== Run

You are now ready to get Spexregister Server up and running:

[source,bash]
----
$ docker compose up -d
----

Keycloak creates the realm from ``fgv.json`` the first time it starts.
The realm lets a locally running https://github.com/bloomper/spexregister-web[spexregister-web], i.e. ``npm run dev``, log in from ``WEB_URL`` in ``.env``, which defaults to ``http://localhost:3000``.
Registration requires a Cloudflare Turnstile challenge.
Locally, Keycloak uses Cloudflare's test keys, which always pass.
To see a failed challenge, set ``TURNSTILE_SECRET_KEY=2x0000000000000000000000000000000AA`` in ``.env`` and run ``docker compose up -d keycloak``.

``./scripts/configure-keycloak.sh`` allows Postman's callback URL in Keycloak (see <<testing_the_api>>).

[[keycloak_migrations]]
=== Keycloak migrations

A change to ``fgv.json`` reaches only realms created after it.
For a realm that already exists, the change comes with a script in ``scripts/migrations/``, named after the date it was added.
Run every script that is newer than the realm, in date order, while Keycloak is running:

[source,bash]
----
$ ./scripts/migrations/2026-10-15-security-passkeys-turnstile.sh
----

The scripts can be run again safely.
Once every environment has run a script, delete it; git history keeps it.
The same scripts for staging and production are in https://github.com/bloomper/spexregister-deploy[spexregister-deploy].

[[sample_data]]
== Sample data

If ``APP_IMPORT_SAMPLE_DATA`` in ``.env`` is set to ``true``, sample data will be imported.
Sample data consists both of real data and random data but none of the data can be traced to real individuals, i.e. no personally identifiable information (PII).

[sidebar]
.NOTE
--
Any existing data and all users in Keycloak will be wiped out, at every start.
--

The import also creates the users listed under <<caddy,Test credentials>> in Keycloak, together with a number of random users.
The realm itself contains no users, so without sample data the first user has to register and be given roles in Keycloak's admin console.

[[keycloak]]
== Keycloak

[[keycloak_customization]]
=== Customization

In order to support passwords from the previous Spexregister generation, a custom password hashing provider has been implemented.
At first login, the password is re-hashed using the default password hashing provider.

The provider lives in https://github.com/bloomper/fgv-keycloak[fgv-keycloak], together with the other Keycloak providers, the realm and the theme.
That repository publishes the Docker image ``bloomper/fgv-keycloak``, which ``docker-compose.yaml`` uses.

[[keycloak_administration]]
=== Administration UI

The administrative UI of Keycloak can be accessed at https://keycloak.fgv.local.nu:8443/auth.
The username is set by ``KEYCLOAK_ADMIN`` in ``.env`` and the password in ``.docker/secrets/KEYCLOAK_ADMIN_PASSWORD``.

[[keycloak_setup]]
=== Setup

These are the steps to create a realm in Keycloak:

* Create realm ``fgv``
** General
*** Display name: FGV
*** HTML display name: Föreningen Gamla Västar
** Login
*** Forgot password: Enabled
*** Email as username: Enabled
*** Login with email: Enabled
** Themes
*** Login theme: FGV
** Localization
*** Internationalization: Enabled
*** Supported locales: English, Swedish
*** Default locale: Swedish
* Create client ``spexregister``
** Enable client authentication
*** The generated secret found under Credentials -> Client Secret is the one to use for any clients
** Create role ``USER``
** Create role ``EDITOR``
** Create role ``ADMIN``
** Disable full scopes (client scopes -> spexregister-dedicated -> Scope -> Full scope allowed -> Off)
* Create client ``fgv-admin``
** Enable client authentication
*** The generated secret found under Credentials -> Client Secret is the one to use for Spexregister Server
** Enable service account roles
** Disable standard flow
** Disable direct access grants
** Assign the following service account roles
*** manage-users
*** query-users
*** view-users
*** view-clients

To export the realm, i.e. ``realm/fgv.json`` in https://github.com/bloomper/fgv-keycloak[fgv-keycloak], do the following:

* Start Keycloak by ``./bin/kc.sh start-dev``
* Follow the steps outlined above
* Export by ``./kc.sh export --users realm_file --file fgv.json --realm fgv``

[[caddy]]
== Caddy

Caddy is used as a web server in front of Keycloak and Spexregister Server and takes care of creating and assigning an SSL certificate.
However, since it is listening to local addresses, the certificate is not created by a proper CA (Certificate Authority).
It is therefore needed to import the root certificate to avoid browsers complaining about the certificate.

The root certificate can be found in ``.docker/caddy/data/caddy/pki/authorities/local/root.crt``.
Import it into your OS's trust manager.

[[mailpit]]
== Mailpit

Mailpit (https://mailpit.axllent.org/) acts as the SMTP server when running locally.
It catches all emails sent by Keycloak, nothing is delivered to real recipients. Spexregister Server sends no emails itself.

The caught emails can be viewed at https://mail.fgv.local.nu:8443 (or http://localhost:8025).

These are the emails sent during self-registration:

|===
|Email|Sent by|Recipient

|Email verification|Keycloak|The registering user
|New user awaiting approval|Keycloak|``admin@fgv.local.nu``, can be changed by setting ``KEYCLOAK_ADMIN_NOTIFICATION_RECIPIENTS`` in ``.env``
|Account approved|Keycloak, when an administrator assigns the user a role|The approved user

|===

[[tests]]
== Tests

There are two types of tests:

* Unit tests, located under ``src/test``
* Integration tests, located under ``src/integrationtest``

Unit tests do not require any external dependencies, such as a database, and are therefore quicker to run.
An example of unit tests is API tests which are used to generate the REST API documentation.
Apart from API tests, unit tests are mostly only written for complex logic.

Integration tests are slow to run as they depend on a full environment but that also means that they are end-to-end tests which are generally considered to provide better test value.

[[testing_the_api]]
== Testing the API

There are many tools out there that can be used for manual testing of the APIs, e.g. Postman (https://www.postman.com/).
The Keycloak client requires PKCE, so the tool must support it.

To use Postman, first run ``./scripts/configure-keycloak.sh``, which allows Postman's callback URL in Keycloak.
Then select ``OAuth 2.0`` as ``Auth Type`` under the ``Authorization`` tab and then select
``Authorization Code (With PKCE)`` as ``Grant type`` and ``SHA-256`` as ``Code Challenge Method``.
Enter values as follows (leave other fields empty).

|===

|Field|Value|Comment

|Callback URL|https://oauth.pstmn.io/v1/browser-callback|
|Auth URL|https://keycloak.fgv.local.nu:8443/auth/realms/fgv/protocol/openid-connect/auth|If ``APP_KEYCLOAK_REALM`` in ``.env`` has been changed, the value must be changed accordingly
|Access Token URL|https://keycloak.fgv.local.nu:8443/auth/realms/fgv/protocol/openid-connect/token|If ``APP_KEYCLOAK_REALM`` in ``.env`` has been changed, the value must be changed accordingly
|Client ID|spexregister|If ``APP_KEYCLOAK_CLIENT_CLIENT_ID`` in ``.env`` has been changed, the value must be changed accordingly
|Client Secret|ip8dFYgp03sVytrrEeXgwHIgHAMtE350|If the secret of the client has been changed in Keycloak, the value must be changed accordingly
|Scope|offline_access|
|Client Authentication|Send as Basic Auth header|

Request an access token by clicking ``Get New Access Token`` and use any of the test credentials to login.
Use the obtained access token when invoking the API endpoints.

|===

[[mcp_server]]
== MCP server

Spexregister Server exposes an MCP (Model Context Protocol) server at ``/api/mcp`` (stateless streamable HTTP),
letting AI assistants manage spex, spex revivals, spex categories, tasks, task categories, news and tags.
Spexare and individual users are intentionally not exposed; the only user-related tool returns aggregated counts
(users per state and accounts pending approval) and requires the admin role.

Every tool call runs with the permissions of the signed-in user, and changes are recorded in the audit history
with source ``MCP``.

Authentication uses OAuth 2.0 against Keycloak with the public client ``spexregister-mcp`` (authorization code with PKCE,
redirect URIs ``http://localhost:*`` and ``http://127.0.0.1:*``). Only tokens issued to that client are accepted
by the MCP endpoint, and they are not accepted by the rest of the API.
The tokens must also have the MCP endpoint's address, i.e. ``APP_BASE_URL`` with the path ``/api/mcp``, as audience.
Keycloak adds it through the client's audience mapper, which ``fgv.json`` sets from ``SPEXREGISTER_MCP_URL``.
Users confirm the access once, on Keycloak's consent page.
MCP clients discover Keycloak through the protected resource metadata at
``/.well-known/oauth-protected-resource/api/mcp``. Keycloak does not allow dynamic client registration by default,
so configure the MCP client with the client id ``spexregister-mcp``.

Locally, the MCP server is available at ``https://api.register.fgv.local.nu:8443/api/mcp``.
It can for instance be explored with the MCP Inspector (https://github.com/modelcontextprotocol/inspector).
